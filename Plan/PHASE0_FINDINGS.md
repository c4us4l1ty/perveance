# Phase 0 — preliminary findings

**Date:** 2026-11-04. This is a feasibility record, not a completed security review. The owner requested using GitHub CI as the Rust compiler because the Arena sandbox has no Rust toolchain.

## Environment observations

- `rustc` and `cargo` are not installed in the Arena environment, and requests to `static.rust-lang.org`, `crates.io` and `index.crates.io` failed there. GitHub Actions is configured to compile/test Rust; CI outcomes must be read from the actual run, not inferred from the workflow file. CI does not prove that the GUI works on a user's desktop or that runtime sandboxing is safe.
- `unshare -Urn` worked during the probe, and the process saw the temporary host sentinel. The isolated network namespace showed only loopback. Namespaces on their own do not isolate the filesystem or establish a sandbox. `bwrap`, `podman`, and `docker` were not found in this environment. `tools/phase0_probe.py` repeats a limited, non-destructive version of these checks; it is not an adversarial suite or certification.
- The current prototype cannot run agent-authored code. Autonomous execution remains unimplemented and disabled; do not treat CI runners as a user-facing sandbox.

## Graphite investigation

At the reviewed [Graphite revision](https://github.com/GraphiteEditor/Graphite/tree/708cca339de55b6bbb3f6257769c45dffa492c3e), its workspace requires Rust 1.98, and `graphene-cli` exposes document compilation and export commands, including PNG and SVG. The desktop UI crate lists a Chromium Embedded Framework dependency, while the editor depends on numerous workspace-internal graph/document crates. This shows an actual headless export path and substantial integration surface, not a verdict on suitability or an indication of a stable external editing API. Graphite has not been built or interactively evaluated in this environment.

A small independent Rust GUI/headless pixel prototype is being used to test product interaction and shared document operations, **not** to declare that Graphite has been rejected or the Phase 0 foundation gate has passed. Compare with a real upstream build and editor/CLI exercise before choosing the final engine. Do not copy Graphite code without the license inventory.

## Model/harness investigation

The reviewed OpenCode source includes an OpenRouter provider implementation. That is evidence of upstream provider support, not evidence that it works through a Perveance credential broker, honors its network restrictions, or meets its security model. No provider credentials, live model call or agent harness were tested.

## Remaining gate

Build and inspect Graphite on CI or a suitable development environment; evaluate document editing and pixel workflows. Select and adversarially test a sandbox backend and broker-compatible harness; test controlled dependencies, resource limits and failure recovery. These tasks remain open. The initial prototype does not enable or claim them.

## Bubblewrap fixed-test feasibility probe

The fixed-code, non-destructive `tools/isolation_probe.py` reports narrow observations and always leaves autonomous execution disabled. It exercises a synthetic host sentinel, workspace, symlink, `/proc` root paths, host IPv4 loopback, and a synthetic environment variable. It is not a production sandbox profile or a security certification. Automated tests also run the fixed worker without isolation against disposable fixtures and verify it detects the missing boundary.

In [CI run 41816238642](https://github.com/c4us4l1ty/perveance/actions/runs/41816238642), bubblewrap was installed but the fixed test did not start: `bwrap: loopback: Failed RTM_NEWADDR: Operation not permitted`. The CI workflow passed because it verifies that this failure is reported and execution remains disabled, **not** because isolation passed. In the Arena development sandbox bubblewrap was not found. These observations do not establish whether another host/configuration can run bubblewrap safely; do not elevate privileges or silently omit network isolation to bypass this failure. No candidate code was executed.

## Workspace Unix-socket escape observation

The earlier v2 diagnostic planted a disposable, listening host Unix-domain socket inside the bind-mounted workspace and treated a successful child connection as a failure. This is an intentionally unsafe workspace fixture, not a claim that all workspaces contain sockets. A separate fixed-worker control in the Arena development environment ran under `unshare -Urn`: the host IPv4 loopback listener was unreachable, but the worker connected to the host Unix socket through the shared filesystem. It also observed the expected readable/writable synthetic host sentinel because this control does not isolate the filesystem. This shows that a network namespace alone does not prevent that IPC route; it does **not** verify bubblewrap or a production sandbox. No user code or real credentials were used.

The v2 diagnostic required the socket access to be blocked as well as the prior checks; if bubblewrap became runnable, the deliberately exposed socket could cause it to fail. A real supervisor would need secure, race-resistant workspace staging, special-file/socket and inherited-FD handling, plus independent threat testing. A passing fixed probe still would not certify isolation or authorize execution.

[CI run 41832022971](https://github.com/c4us4l1ty/perveance/actions/runs/41832022971) passed the workflow, but its separate unshare Unix-socket control was **skipped** because unprivileged user/network namespaces were unavailable. The bubblewrap probe itself again failed before the worker started (`Failed RTM_NEWADDR: Operation not permitted`). Neither result validates the bwrap socket boundary on CI; the socket reachability observation above is from the local development environment only.

## Runner comparison and corrected socket controls (v3)

The old positive test put a live host socket directly into its bound workspace. Since a network namespace does not itself prevent access to a pathname Unix socket, that fixture was deliberately unsafe and could not demonstrate the behavior of a clean staged workspace. The v3 diagnostic constructs a separate temporary workspace with a fixed file and a malicious symlink but no host socket; its positive test checks the staged file, workspace writes, sentinel/symlink/proc visibility, host loopback and direct host-socket path, and environment clearing. It then runs a separate unsafe-workspace control, requiring the deliberately exposed socket to be reachable while the other checks still pass. The clean result means the socket was absent from that fixture, **not** that arbitrary mounted workspaces are safe. This is not the Rust staging primitive and does not validate staging of real project inputs or close inherited descriptors.

In [matrix run 41839699568](https://github.com/c4us4l1ty/perveance/actions/runs/41839699568), unprivileged bubblewrap passed the fixed v3 checks on Ubuntu 22.04 (kernel `6.8.0-1070-azure`, bwrap `0.6.1`, AppArmor userns restriction `0`) and Ubuntu 26.04 (kernel `7.0.0-1019-azure`, bwrap `0.11.1`, restriction `1`). Ubuntu 24.04 (kernel `7.0.0-1017-azure`, bwrap `0.9.0`, restriction `1`) failed before the worker at `Failed RTM_NEWADDR: Operation not permitted`. These are observations on specific hosted runners, not guarantees for every machine with those versions; the common restriction value on 24.04 and 26.04 is insufficient by itself to establish root cause. The matrix checked the installed helper was not setuid/setgid or file-capability-enabled, did not change the host security policy, and retained network isolation. The workflow reports all results; a successful workflow alone is not evidence of a passed diagnostic.

Ubuntu 26.04 is now the selected **CI diagnostic image** for a required fixed-probe canary; the other images remain comparisons. This supplies a test environment for further work, not a production platform recommendation or a fix for every Ubuntu 24.04 host. Never silently drop `--unshare-net`, enable setuid, globally disable AppArmor restrictions, or run unsandboxed when the probe fails. Real security gates still require a trusted supervisor, race-resistant staging and FD handling, cgroup/resource limits, broker, broad adversarial tests and crash recovery. Autonomy remains disabled regardless of probe result.

A separate explicitly opted-in Rust integration test now uses `workspace::stage_project` to stage an actual synthetic project with a hidden layer and transparent pixel. On the selected Ubuntu 26.04 runner, a fixed bubblewrap worker read the staged content, wrote a scratch file, could not reach a host TCP loopback listener or the original Unix socket path, did not see a synthetic environment sentinel, and the test checked cleanup and host sentinel integrity. Host controls verified both listeners were reachable before launch. [Matrix run 41840023372](https://github.com/c4us4l1ty/perveance/actions/runs/41840023372) passed this required test and the fixed probe, while Ubuntu 24.04 still failed the diagnostic. The test does not run generated code, test arbitrary paths, defend against same-user races, enforce resource limits, or validate a production sandbox. No claim about other hosts follows from this result.

## Fixed-worker lifecycle and descriptor control

A new fixed-code-only Rust diagnostic stages an actual project, invokes bubblewrap with the network namespace retained, applies per-file output limits, validates the fixed worker's summary, and attempts timeout/cancellation, reaping and cleanup. On the selected Ubuntu 26.04 runner, [matrix run 41842202968](https://github.com/c4us4l1ty/perveance/actions/runs/41842202968) passed fixed completion, failure, output-limit, timeout, cancellation, cleanup, CLI and one intentionally inheritable synthetic host-file descriptor test. Before adding `close_range` close-on-exec to the launcher, [matrix run 41841878127](https://github.com/c4us4l1ty/perveance/actions/runs/41841878127) failed the fixed worker's unexpected-descriptor check; this demonstrated why relying on inherited-FD assumptions was unsafe. The fixed worker now checks for extra open descriptors, and the launch fails if the syscall is unavailable or blocked. This is evidence for a narrow fixed scenario, not a full FD audit, hard deadline, cgroup resource enforcement, descendant cleanup proof, or production sandbox. No model or arbitrary code was run, and autonomy remains disabled.

The follow-up [matrix run 41842647426](https://github.com/c4us4l1ty/perveance/actions/runs/41842647426) added a direct negative control: on that Ubuntu 26.04 runner, bare bubblewrap passed the intentionally inheritable synthetic file descriptor into the fixed child, while the new launcher's close-on-exec handling left no extra descriptor in its fixed child. This concerns that specific helper/version and invocation, not all bubblewrap versions or all descriptor channels.

## Arena development sandbox fixed-probe experiment

In this Arena session, a temporary unprivileged diagnostic build of bubblewrap was compiled locally from upstream commit `362936aea0d5c6e70f7af75d2d44b5a914cb4ba2` (v0.13.1), using GCC, the system `libcap.so.2` and a header from the pinned GitHub libcap mirror commit `8c67abc3f5cfa8310dae21e5db464fd990cb71a2`. It was built outside the repository with a minimal local configuration, not installed, setuid, given file capabilities or independently audited. With that binary temporarily on PATH, `tools/isolation_probe.py` v3 passed the clean fixed checks, and its unsafe-workspace control observed the host Unix socket was reachable. This is a real but narrow observation for this Arena sandbox, not a production sandbox certification or a guarantee about other sessions; the Python diagnostic used its PATH-selected binary, whereas the Rust fixed-worker diagnostic still requires `/usr/bin/bwrap` and was not run locally. It does not prove cgroup quotas, safe untrusted builds, trusted supervision or a complete FD/escape audit. Autonomous execution remains disabled.
